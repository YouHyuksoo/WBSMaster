# AI 채팅 재구성 설계 (지성지식관리 연동 1단계)

- 작성일: 2026-11-09
- 상태: 초안 (사용자 승인 전)
- 범위: WBS Master 저장소만 수정한다. 지성지식관리(`C:\Project\ai-knowledge-platform`) 연동은 2단계 설계에서 따로 다룬다.

## 1. 왜 하는가

WBS Master의 AI 어시스턴트(`/dashboard/chat`)는 질문을 잘못 알아듣고 틀린 답을 한다. 사용자 말로는 "관계, 맥락, 오타에 취약하고 어떤 때는 맞고 어떤 때는 틀린다."

최종 목표는 지성지식관리를 회사 공용 지식 서버로 키우고, WBS Master를 그 서버를 쓰는 첫 번째 업무 시스템으로 만드는 것이다. 작업 순서는 사용자와 아래처럼 정했다.

1. **이번 문서**: 채팅을 "도구를 골라 쓰는 구조"로 바꾼다. 지식 서버 없이도 풀리는 실패를 여기서 푼다.
2. **다음 문서**: 지성지식관리에 업무 레코드 수집 경로를 만들고, 의미·관계 검색을 채팅 도구 하나로 붙인다.

### 1.1 현재 상태 (2026-11-09 확인)

파이프라인(`src/lib/llm/index.ts`의 `processChatMessage`)은 이렇게 돈다. LLM이 테이블을 고르고, LLM이 SQL을 생성하고, `validateSQL`(정규식 검사)을 거쳐 실행하고, 결과를 LLM이 분석한다.

- 이전 대화를 LLM에 넘기지 않는다. 매 요청이 질문 한 줄이다.
- 의도 구분이 없다. 잡담도 SQL로 바꾼다. 실제 기록을 보면 "대답이 너무 늦은데"라는 말에 `notifications` INSERT를 시도했다.
- 검색은 SQL `=`/`ILIKE`뿐이다. 오타와 비슷한 말을 찾지 못한다.
- JOIN과 UNION을 LLM이 직접 짠다. 실제로 서로 다른 Enum 타입을 UNION하다가 오류가 났다.
- 진도율·지연율 같은 계산 지표를 LLM이 SQL로 지어낸다. 1월 피드백 로그에 `column "day" does not exist`, `column "weeknumber"...` 오류가 남아 있다. 화면은 이 지표를 `src/app/api/wbs/schedule-stats/route.ts`에서 계산한다.
- 쓰기 경로에 구멍이 있다. 아래 두 가지가 겹쳐서, LLM이 만든 INSERT/UPDATE가 DB에 그대로 실행될 수 있다.
  - `validateSQL`이 INSERT와 UPDATE를 허용한다.
  - `runSafeSql`은 읽기 전용이 아닌 일반 트랜잭션이다. `route.ts`는 `INSERT INTO "TASKS"`를 정규식으로 감지하고, 서비스 계층 호출이 실패하면 LLM SQL을 그대로 실행한다.
- `schema-info.ts`(1,751줄)에는 베트남 시절 테이블과 틀린 이름이 섞여 있다. `chat_history`/`chat_feedback`은 실제로는 `chat_histories`/`chat_feedbacks`다.
- 기본 모델이 `openrouter/free`다. 응답에 12~291초가 걸리고 품질이 들쭉날쭉하다.

### 1.2 시험 결과

로컬 DB를 읽기 전용으로 놓고 실제 설정(OpenRouter free)으로 질문 11개를 돌렸다. 맞은 것은 3개다.

| 유형 | 질문 | 결과 |
|---|---|---|
| 잡담 | 대답이 너무 늦은데 | ❌ 지연 태스크 SQL 실행 |
| 집계 | 이슈 상태별 건수 | ✅ |
| 관계 | 유혁수가 담당한 요구사항과 이슈 | ❌ UNION Enum 타입 오류 |
| 관계 | 다크모드 관련 요구사항과 이슈 연결 | ❌ DB 미조회, 일반론 생성 |
| 맥락 | 열린 이슈 보여줘 → 그중 긴급한 것만 | ✅ → ❌ (둘째 질문에서 태스크 테이블을 조회) |

이 질문들은 1월에 넣은 웹 개발 샘플 데이터(다크모드, 2FA 등)를 대상으로 했다. 그래서 회귀 기준이 아니라 **실패 유형의 증거**로만 쓴다. 1월 피드백 로그도 지금은 없는 베트남 데이터를 가리키므로 유형만 참고한다.

## 2. 목표 / 비목표 / 반목표

### 목표
- G1. 질문의 의도를 가른다. 대상은 잡담, 조회, 계산 지표, 쓰기 요청, 그 밖의 질문이다.
- G2. 최근 대화를 이어받아 "그중", "아까 그거" 같은 말을 이해한다.
- G3. 자주 묻는 조회와 계산은 미리 만든 도구로 답한다. 계산 지표는 **화면과 같은 숫자**를 낸다.
- G4. 사람 이름의 오타와 한국어 표현을 흡수한다. 사람 이름은 퍼지 매칭으로 찾고, 한국어 용어는 Enum으로 바꾼다(예: 긴급 → `CRITICAL`/`HIGH`).
- G5. 등록과 수정은 도구로만 하고, 사용자가 확인 카드를 눌러야 실행된다.
- G6. 자유 SQL은 마지막 수단으로 남기되, **DB 수준에서 읽기 전용**으로 실행한다.
- G7. 회사 ChatGPT 구독 계정 하나를 서버 공용 LLM으로 쓴다.
- G8. 2단계의 "지식 검색" 도구를 코드 수정 없이 등록만으로 꽂을 수 있게 한다.

### 비목표
- 의미 검색(임베딩)과 그래프 검색. 이건 2단계에서 지성지식관리로 한다. 이번에는 사람 이름 퍼지 매칭과 용어 사전까지만 한다.
- 채팅 화면의 전면 재디자인. 확인 카드와 후보 선택 UI만 추가한다.
- 베트남 잔재 기능과 코드 삭제. 채팅이 보는 스키마 설명에서만 뺀다.

### 반목표 (기술적으로 돌아가도 실패로 본다)
- 사용자가 확인하지 않았는데 DB가 바뀐다.
- 채팅이 화면과 다른 진도율·지연율을 말한다.
- 다른 프로젝트 데이터가 답에 섞인다.
- 지금 맞는 단순 집계("이슈 상태별 건수")가 틀리게 된다.
- ChatGPT 연결이 끊기면 채팅 전체가 멈춘다.

## 3. 제약

- Next.js 16 App Router, Prisma 7, PostgreSQL. 운영은 지성 IDC의 PM2 단일 프로세스(fork, 3020)다.
- API 인증은 `requireAuth()`를 쓰고, 프로젝트 권한은 `assertProjectAccess(projectId, user)`를 쓴다.
- 파일당 200줄을 권장하고 300줄을 넘으면 나눈다. 파일 상단에는 한국어 JSDoc을 단다(AGENTS.md).
- Prisma 필드를 추가하면 `schema.prisma`, `api.ts`, `hooks/use*.ts`를 함께 고친다.
- 비밀값(토큰, 키)은 코드, 로그, DB 평문, git에 남기지 않는다.
- 테스트는 실제 외부 LLM과 사용자 실데이터를 쓰지 않는다. LLM을 부르는 평가는 사용자가 명시적으로 실행하는 별도 스크립트로 둔다.

## 4. 사용자가 정한 것

- 지성지식관리는 **기존 시스템을 공용 서버로 키운다**. WBS Master 전용으로 따로 만들지 않는다. (2단계)
- 순서는 **채팅 재구성 먼저, 지식 서버 연동 나중**이다.
- 채팅에서 **등록과 수정을 허용**한다.
- LLM은 **ChatGPT 구독 계정(OAuth)**을 쓴다. 내부 서버이고, **회사 계정 하나를 모든 사용자가 같이 쓴다.**
- 지식 서버 반영은 주기적인 스케줄 없이 **즉시 반영하고, 실패한 것은 큐에 남긴다**. (2단계)
- 색인 범위와 메뉴 판단은 코드와 데이터를 보고 Claude가 정한다. (2단계에 반영)

## 5. 설계

### 5.1 전체 흐름

```
POST /api/chat
  └ 대화 맥락 로드 (같은 사용자·프로젝트의 최근 N턴)
  └ 에이전트 루프 (LLM ↔ 도구, 최대 K회)
       ├ 읽기 도구: 바로 실행하고 결과를 LLM에 돌려준다
       ├ 쓰기 도구: 실행하지 않고 "제안(pending action)"으로 저장해 확인 카드로 응답한다
       └ 도구가 없으면 답변만 한다 (잡담, 도움말)
  └ 응답: 마크다운 + (차트 | 마인드맵 | 확인 카드 | 후보 선택)
POST /api/chat/actions/{id}/confirm  → 서비스 계층으로 실행
POST /api/chat/actions/{id}/cancel
```

의도 분류를 따로 호출하지 않는다. 도구 목록을 받은 LLM이 도구를 고르게 하는 방식(function calling)으로 G1을 푼다. 잡담은 도구 없이 답한다.

### 5.2 LLM 제공자: 회사 ChatGPT 계정

- 새 제공자 `chatgpt`를 추가한다. Responses API(`https://chatgpt.com/backend-api/codex/responses`)를 OAuth access token으로 호출한다.
- **로그인**: 관리자 전용 설정 화면에서 OAuth 디바이스 코드 로그인을 한다. 서버가 URL과 코드를 보여 주면 관리자가 회사 계정으로 승인한다.
- **토큰 저장**: 저장소 밖 파일(환경 변수 `CHATGPT_AUTH_FILE`, 서비스 계정만 읽고 쓰기)에 둔다. DB와 로그에는 남기지 않는다.
- **갱신**: refresh token은 한 번 쓰면 바뀐다. 그래서 갱신은 서버 한 곳에서만 하고, 프로세스 안 뮤텍스와 파일 잠금으로 동시 갱신을 막는다. 개발자 PC의 Codex `auth.json`을 복사해 쓰지 않는다(한쪽이 로그아웃된다).
- **선택 방식**: 이 제공자는 시스템 공용이다. 사용자별 `ai_settings`에는 키 없이 provider 값 `chatgpt`만 고르게 한다. 새 사용자의 기본값도 `chatgpt`다.
- **대비 경로**: 401(재로그인 필요), 429, 연결 실패가 나면 관리자가 지정한 API 키 제공자(기존 OpenAI/OpenRouter 등)로 한 번 넘긴다. 응답에 "대체 모델로 답함"을 표시하고, 관리자 화면에 연결 상태를 보여 준다.
- **확인할 것 (구현 첫 작업)**: 회사 계정 요금제에서 쓸 수 있는 모델, Responses API의 도구 호출 동작, 스트리밍 여부. 도구 호출이 안 되면 이 설계는 다시 논의한다.
- 공식 지원 경로가 아니어서 예고 없이 바뀔 수 있다. 모든 사용자가 회사 계정 하나의 할당량을 같이 쓴다. 사용자는 이 위험을 알고 선택했다.

### 5.3 LLM 클라이언트 추상화

- 지금의 `LLMClient`는 "프롬프트 → 텍스트"다. 여기에 "메시지 + 도구 정의 → 텍스트 또는 도구 호출"을 추가한다.
- 도구 호출은 `chatgpt`(Responses)와 `openai`/`openrouter`(chat completions tools) 세 제공자에 먼저 구현한다. Gemini와 Mistral은 도구 호출이 없는 지금 파이프라인으로 처리한다. 제공자마다 다른 형식은 어댑터 안에 가둔다.

### 5.4 대화 맥락

- 같은 사용자·프로젝트의 `chat_histories`에서 최근 N턴(기본 6턴)을 메시지로 넣는다.
- 지난 턴에서 도구가 돌려준 결과가 길면 그대로 넣지 않고 요약만 넣는다. 예를 들면 "이슈 6건 조회: ISS-008, ISS-010… (status=OPEN)" 같은 식이다. 그래서 "그중"이 무엇을 가리키는지 알 수 있다. 이를 위해 `chat_histories`에 도구 호출 요약 칼럼(JSON)을 추가한다.

### 5.5 도구 목록 (처음 범위)

도구는 `src/lib/chat-tools/` 아래에 하나씩 두고, 레지스트리에 등록한다. 모든 도구는 서버가 주입한 `projectId`와 `user`로만 동작한다. LLM이 projectId를 고를 수 없다.

**읽기**
| 도구 | 하는 일 |
|---|---|
| `find_people` | 이름이나 일부로 프로젝트 구성원(users + team_members)을 찾는다. 퍼지 매칭(편집 거리, 자모 분해 비교)으로 후보와 점수를 돌려준다 |
| `list_wbs` | WBS 항목을 조회한다. 레벨, 상태, 담당자, 기간, 지연 여부로 거른다 |
| `wbs_schedule_stats` | 계획 진척률, 실적 진척률, 지연율, 달성률. `schedule-stats` 라우트의 계산을 `src/lib`로 옮겨 화면과 같은 함수를 쓴다 |
| `list_issues` | 이슈사항(issues) 조회 |
| `list_field_issues` | 고객이슈 조회 |
| `list_customer_requirements` | 고객요구사항 조회 |
| `list_discussion_items` | 협의요청 조회 |
| `list_milestones` | 마일스톤과 타임라인 조회 |
| `list_as_is_items` | AS-IS 총괄 항목 조회 |
| `get_record` | 코드(ISS-011 등)나 ID로 레코드 하나를 상세 조회 |
| `run_readonly_sql` | 위 도구로 안 되는 질문에만 쓰는 자유 SQL. 5.7 참조 |

조회 도구의 필터 인자는 Enum 값을 받는다. LLM에는 도구 설명 안의 **한국어 용어 → Enum 사전**을 준다(긴급 → `CRITICAL`,`HIGH` / 열린 → `OPEN`,`IN_PROGRESS` / 완료 → `RESOLVED`,`CLOSED` 등). 사전은 각 대시보드 모듈의 `constants.ts` 라벨에서 만들어, 화면 라벨과 어긋나지 않게 한다.

**쓰기 (확인 후 실행)**
| 도구 | 하는 일 |
|---|---|
| `propose_create_issue` / `propose_update_issue` | 이슈 등록, 상태·담당자·우선순위 변경 |
| `propose_create_field_issue` / `propose_update_field_issue` | 고객이슈 |
| `propose_create_discussion_item` / `propose_update_discussion_item` | 협의요청 |
| `propose_create_task` / `propose_update_task` | TASK 관리(칸반) 태스크(`tasks`). 기존 `taskService.createTask`를 쓴다. WBS 항목과 진도 태스크는 이번 쓰기 범위에 넣지 않는다 |

### 5.6 쓰기 확인 흐름

1. LLM이 `propose_*`를 부르면 서버가 인자를 검증한다. 검증 내용은 필수값, Enum, 사람 ID 존재 여부, 프로젝트 권한이다.
2. 사람 이름이 애매하면(후보 2명 이상, 또는 최고 점수가 기준 미만) 제안을 만들지 않고 **후보 선택**으로 응답한다.
3. 검증을 통과하면 `chat_pending_actions` 테이블에 제안을 저장한다. 저장하는 값은 종류, 정규화된 인자, 요청자, 프로젝트, 만료 시각(30분)이고, 확인 카드로 응답한다.
4. 사용자가 [등록]을 누르면 confirm API가 요청자 일치, 만료, 미실행 여부를 다시 확인하고 **화면과 같은 서비스 계층 함수**를 부른다. 알림과 후처리도 화면과 똑같이 돈다. 결과는 대화에 기록한다.
5. 서비스 계층이 없는 엔티티(이슈, 고객이슈, 협의요청)는 기존 Route Handler의 생성·수정 로직을 `src/lib/services/`로 빼서 화면과 채팅이 같은 함수를 쓰게 한다.

### 5.7 자유 SQL 안전장치

- `validateSQL`이 SELECT/WITH만 허용하도록 바꾼다. INSERT/UPDATE 허용을 제거한다.
- `route.ts`의 `INSERT INTO "TASKS"` 정규식 감지와 실패 시 LLM SQL 실행 폴백을 삭제한다.
- `run_readonly_sql`은 `SET TRANSACTION READ ONLY` 트랜잭션 안에서 실행하고 `statement_timeout`도 건다. 정규식 검사는 보조 수단이다. 기존의 비밀번호 차단(`users` 임시 뷰, `redactSensitive`)은 유지한다.
- `projectId` 조건은 LLM에 맡기지 않는다. 프로젝트 소속 테이블을 조회하면 결과에 다른 projectId가 섞였는지 서버가 검사하고, 섞였으면 거절한다.

### 5.8 스키마 설명 정리

- `schema-info.ts`는 `run_readonly_sql`에서만 쓴다. 대상 테이블은 "색인·조회 대상"으로 정한 것만 남긴다. 베트남 잔재(업무기능추적표, AS-IS 상세 13개 테이블)와 설정·알림·채팅 테이블은 뺀다.
- 테이블 이름이 실제 DB와 맞는지 검사하는 단위 테스트를 추가한다. `@@map` 목록과 대조해서 `chat_history` 같은 어긋남이 다시 생기지 않게 막는다.

### 5.9 화면 변경 (최소)

- 확인 카드: 요약 문장, 바뀌는 필드 표, [등록]/[취소]. 실행 후에는 결과 링크를 보여 준다.
- 후보 선택: 사람 후보 버튼. 누르면 그 선택을 다음 메시지로 보낸다.
- 대체 모델 표시와 관리자용 ChatGPT 연결 상태 및 로그인 화면.
- 기존 차트, 마인드맵, 엑셀 다운로드, 페르소나, 피드백은 그대로 둔다.

## 6. 평가 (성공 기준)

- 전용 **평가 픽스처**를 만든다. 오창 MES 업무에 맞는 가짜 프로젝트 하나에 WBS, 이슈, 고객이슈, 협의요청, 구성원을 넣는다. 일부러 비슷한 이름도 넣는다(예: 최종무/최종우). 픽스처는 별도 DB 스키마나 별도 데이터베이스에만 넣고, 사용자 실데이터에는 쓰지 않는다.
- 질문 세트는 30개 안팎으로, 유형별(잡담, 집계, 관계, 맥락 2~3턴, 오타, 용어, 계산 지표, 쓰기 제안, 후보 선택)로 나눈다. 질문마다 **기대 결과**를 기계로 판정할 수 있게 적는다. 기대 결과는 레코드 ID 집합, 건수, 지표 값(화면 계산과 같은 값), 호출돼야 하는 도구, DB가 바뀌지 않아야 함 같은 것들이다.
- LLM은 결정적이지 않으므로 질문마다 3회 돌려 통과율을 낸다.
- 평가 스크립트(`scripts/eval-chat.ts`)는 실제 LLM을 부르므로 사용자가 직접 실행할 때만 돈다. CI와 `npm test`에는 넣지 않는다.
- 합격선(제안): 전체 통과율 85% 이상, 반목표 위반 0건(확인 없는 DB 변경, 다른 프로젝트 데이터 노출, 화면과 다른 지표).
- 단위 테스트(Vitest, LLM 목): 도구 인자 검증, 퍼지 매칭, 용어 사전, 확인 흐름(만료, 다른 사용자, 이중 실행), 읽기 전용 SQL 거절, 스키마 이름 대조.

## 7. 2단계와의 접점

- 도구 레지스트리에 `search_knowledge`(지성지식관리 하이브리드 검색 호출)를 추가하는 것으로 연동한다.
- 2단계에서 할 일: 지성지식관리에 레코드 upsert/delete API 추가, WBS Master에 outbox 테이블과 Prisma 확장으로 즉시 전송, 실패분 큐 재전송, import 스크립트 뒤 프로젝트 전체 재색인.

### 5.10 Claude가 정한 세부 사항 (사용자 확인 전)

- **대체 경로 설정**: 시스템 설정 테이블을 새로 만들지 않는다. 서버 `.env.local`의 `CHAT_FALLBACK_PROVIDER`와 해당 제공자 API 키 환경 변수로 지정한다. 비어 있으면 대체 없이 "ChatGPT 연결 끊김, 관리자에게 재로그인 요청" 안내를 낸다.
- **디바이스 코드 로그인**: Codex CLI와 같은 공개 OAuth client를 쓴다. 정확한 엔드포인트와 client id는 구현 첫 작업에서 확인하고 코드 상수로 둔다(비밀값 아님).
- **기존 사용자 프롬프트**: `ai_settings.sqlSystemPrompt`는 `run_readonly_sql` 도구 안에서만 쓴다. `analysisSystemPrompt`와 페르소나 프롬프트는 에이전트 루프의 시스템 메시지 뒤에 붙인다. 도구 규칙(확인 없이 쓰기 금지 등)은 사용자 프롬프트보다 앞에 두고 덮어쓸 수 없게 한다.
- **Gemini·Mistral 사용자**: 도구 호출과 대화 맥락 없이 기존 파이프라인을 유지한다. 다만 5.7의 쓰기 차단과 읽기 전용 실행은 똑같이 적용한다.
- **스트리밍**: 이번 범위에서는 하지 않는다. 지금처럼 완성된 응답을 한 번에 돌려준다.
