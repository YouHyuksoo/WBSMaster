# 채팅 음성 출력 진단 — 전체 재시작 후 청취 복구 확인

- 작성일: 2026-11-11
- 상태: 완료. EGO 전체 재시작 후 사용자가 “소리나옴”으로 실제 청취 복구를 확인했다. 앱 코드 수정 없음.
- 확인 HEAD: `2dbc297406214f3bfa3980dbbb4fa80e26cef08e`.
- 증상: 사용자가 채팅 답변 아래 스피커 버튼을 눌러도 소리가 들리지 않는다고 보고.

## 확인한 근거

- `useOpenAIVoice.ts`의 `POST /api/voice/speak`와 서버 POST 핸들러가 일치한다.
- localhost:3000의 로그인 상태에서 OpenAI 키 등록 여부는 true. 키 원문은 조회·출력하지 않았다.
- 스피커 버튼을 통해 합성 입력만 짧은 진단 문장으로 바꾸어 실제 요청을 한 번 확인했다. 응답 200, audio/mpeg, 28,800바이트, 길이 1.8초.
- 브라우저 이벤트: play → loadedmetadata → canplay → playing → ended. 재생 시각은 1.8초까지 진행했고 HTMLAudioElement의 muted=false, volume=1, media error 없음.
- 브라우저 Media Internals에서도 MP3 24kHz mono 디코딩, kPlaying과 kEnded가 확인됐다. 같은 브라우저의 운영 주소 음성 재생 기록에도 16.56초 재생 완료가 있었으나 운영 서버 소스·배포 상태를 확인한 것은 아니다.
- Windows 기본 출력의 음소거는 false, 음량은 65%. 기본 출력의 앱별 음량 조회에서는 EGO 소리 세션을 찾지 못했다. 이 사실만으로 원인을 확정하지 않는다.
- localhost 사이트의 소리 설정은 자동(기본값). 사이트 권한·OS 볼륨·음소거 설정을 바꾸지 않았다.
- OpenAI와 무관한 별도 Web Audio 확인음도 브라우저 running 상태로 실행했다. 실제 청취 결과는 사용자 응답이 필요하다.
- `src/lib/openai-voice.test.ts`의 5개 테스트 통과.

## 제어 오류와 현재 상태

- Windows 창 제어에서 `coordinate input geometry is unavailable` 및 창 위치 불일치가 발생했다. 창을 다시 선택한 뒤 관찰했으며 소리 설정은 변경하지 않았다.
- 진단용 fetch/Audio 관찰 코드는 localhost 진단 탭 새로고침으로 제거했다.
- EGO TaskSpace 29 (`WBS chat speech diagnosis 20261111`)를 사용자에게 handOff했다.
- p1: localhost 채팅, p2: 브라우저 확인음 진단 페이지. p2에 ‘확인음 재생’ 버튼을 표시했다.
- handOff 중이므로 임의로 제어를 재개하거나 finish하지 않는다. 사용자 청취 응답 후 같은 공간을 이어서 사용한다.

## 다음 확인

1. 사용자가 직접 누른 확인음이 들리는지 확인한다.
2. 확인음도 안 들리면 브라우저/출력 경로를, 확인음은 들리면 합성 음성의 실제 파형과 해당 사용자 탭을 추가 대조한다.
3. 원인을 입증한 다음 필요한 부분만 수정하고 실제 청취까지 확인한다.

## 사용자 후속 확인

- 사용자가 별도 확인음도 들리지 않는다고 답했고, 이어서 “ego lite 브라우져에서만 안들리네”라고 확인했다.
- WBS 합성 음성에 한정된 문제가 아니라 EGO Lite의 출력 경로를 우선 조사한다. 확인된 앱 코드 결함은 없다.
- TaskSpace 29를 한 번 재개했으나 이후 EGO가 다시 `Control of this task space is with the user`라고 응답했다. 이 중단은 우회하거나 자동으로 다시 제어권을 가져오지 않는다.
- 조작권 재개 선택을 사용자에게 요청했다. 사용자 승인 뒤 같은 공간을 재개해 사이트 소리 기본값, 탭·공간별 음소거, 출력 경로를 확인한다.

의심: 음성 파일 생성·디코딩·시간 진행 성공을 실제 스피커 출력 성공으로 오인할 수 있다.

프로브: API 메서드·경로, 실제 합성 응답, media 이벤트·음소거·음량, Media Internals, Windows 기본 출력과 앱별 세션, 별도 확인음을 대조했다.

결과: API 실패와 HTMLAudioElement 재생 오류는 진단 요청에서 재현되지 않았다. 실제 무음 원인은 아직 미확정이다.

재발방지: 원인 확인 전 임의의 코드 수정이나 제공자 전환을 하지 않았다. 사용자 청취 응답 후 동일 조건으로 검증을 이어간다.

## 조작 재개 후 추가 확인

- 사용자의 “계속확인해” 요청으로 동일한 TaskSpace 29를 재개했다.
- 브라우저 전역 소리 설정은 허용이며 차단 예외는 없었다. 기본 출력은 Speaker(Realtek(R) Audio)였고 기본 출력 지정 Web Audio도 실행 상태로 진행했다.
- Media Internals에서 활성 입력·출력 스트림이 없는 시점에 실행 파일·부모 PID·AudioService 인수를 검증하고 EGO 오디오 유틸리티 프로세스 PID 27008만 종료했다. 브라우저 전체는 종료하지 않았다.
- 다음 확인음 실행 시 오디오 서비스가 PID 40700으로 다시 생성됐다. 확인음의 AudioContext 시간과 출력 타임스탬프는 진행했다. 이것만으로 실제 청취 복구를 확정하지 않는다.
- Windows 설정 앱 실행은 대상 창을 노출하지 못했다. 설정 변경은 하지 않았다.
- localhost 채팅 p1을 전면으로 가져온 뒤 TaskSpace 29를 사용자에게 handOff했다. p2는 chrome://media-internals 진단 페이지다.
- 사용자가 WBS 스피커를 다시 눌러 청취할 차례다. 전체 EGO 재시작은 다른 열린 작업에 영향을 주므로 선택을 요청했으며 아직 실행하지 않았다.

## 전체 재시작 결과

- 사용자가 오디오 서비스 리셋 후에도 무음이라고 확인하고, 전체 재시작 질문에 “숭인해”라고 승인했다.
- `chrome://restart` 이동은 `net::ERR_INVALID_URL`로 거부됐다. Windows 종료·재실행 경로로 변경한다고 사용자에게 알렸다.
- EGO 창에 정상 종료를 요청했다. 창은 사라졌으나 백그라운드 루트 PID 14788이 남아 실행 파일 경로를 재검증하고 해당 프로세스를 종료했다. 같은 설치 실행 파일을 다시 실행해 새 루트 PID 40168을 확인했다.
- 재시작 후 EGO API 연결은 성공했다. 공간 목록은 사용자 공간 0(새 탭)만 반환했고 기존 공간 29 조회는 `task space not found: 29`로 실패했다.
- 기존 공간이 복원되지 않아 임의로 대체 공간을 만들지 않았다. 사용자의 채팅 재열기 및 후속 확인이 필요하며 실제 청취 복구는 미확인이다.

## 최종 확인

- 전체 재시작 후 사용자가 “소리나옴”이라고 답해 실제 청취 복구를 확인했다. 앞선 청취 대기·재검증 중단 상태를 이 결과로 종료한다.
- WBS 앱 코드는 변경하지 않았다. 오디오 서비스 단독 리셋은 효과가 없었고 EGO 전체 재시작 뒤 복구됐다. 브라우저 내부의 구체적 결함 원인은 확정하지 않았다.
- 기존 TaskSpace 29는 재시작 후 존재하지 않아 finish를 호출할 수 없었다. 대체 작업공간은 만들지 않았다.
- 재발방지: 재생 완료 이벤트를 청취 성공으로 간주하지 않고 사용자 청취까지 확인했다. 동일 증상이 재발하면 EGO 전체 재시작으로 복구됐던 사실을 진단 근거로 사용한다. 영구적인 결함 수정은 수행하지 않았다.
