## 최종 동작

WBS 업무 변경 → PostgreSQL 트리거가 같은 트랜잭션에 outbox 기록 → 커밋 알림(LISTEN/NOTIFY) → WBS 작업자가 기존 지식관리 API로 전송 → 기존 Ollama `bge-m3` 및 Neo4j에 저장 → 채팅의 `search_knowledge` 도구로 의미·관계 검색.

- 주기 cron이나 반복 스케줄은 등록하지 않았다. 실패 시에만 지연 재시도한다.
- 업무 변경과 수집 이벤트를 원자적으로 묶고, 성공한 INSERT/UPDATE와 DELETE 시점을 구분한다. 부모 삭제·프로젝트 이동 시 하위 레코드의 이전 범위도 기록한다.
- 서버가 프로젝트 범위를 정하며 요청·응답 양쪽에서 범위를 검사한다. 지식 검색과 원본 DB 조회는 함께 유지한다. 최신 정확한 건수·진도율은 기존 DB 도구를 사용한다.
- 비밀번호·API 설정·개인 문서는 수집하지 않는다. 문서함은 메타데이터만 대상이며 첨부 파일 본문을 새로 읽어 넣는 기능은 이번 범위에 없다.
- 전송 완료 이벤트의 본문은 비우고, 실패 이벤트는 재전송을 위해 보존한다. 삭제 후 오래된 이벤트가 자료를 되살리지 않도록 revision/tombstone을 사용한다.

## 장애와 처리 내역

- 운영 venv에 pytest와 HTTP 테스트 의존성이 없었다. 운영 의존성을 바꾸지 않고 배포 임시 폴더의 격리된 순수 Python 테스트 도구로 검증했다.
- C: 빌드 폴더에서 D: node_modules junction을 사용할 때 webpack의 드라이브 간 경로 해석이 실패했다. 작업 전용 빌드 폴더를 같은 D: 드라이브에 만들고 빌드 통과 후 교체했다. 이 실패 중 기존 서비스는 유지했다.
- SSH에서 최초 백그라운드 빌드 명령의 응답은 timeout이었다. 상태 파일로 실행 결과를 확인했으며 중복 실행하지 않았다. 이후 일회성 숨김 WMI 프로세스로 빌드를 실행했다. 반복 작업이나 스케줄러는 등록하지 않았다.
- 지식관리 키는 서버 환경 변수에서 공급되고 있었다. 기존 값을 프로세스 메모리에서 읽어 WBS의 ignored `.env.local`에 저장했고 값은 출력하지 않았다. 빌드용으로 만든 환경 파일 사본 2개는 정리했다.
- **기존 UI 문제:** 떠 있는 위젯 메뉴가 전송 버튼의 일부를 가려 클릭 검증이 막혔다. 현재 작업에서 UI 소스는 수정하지 않았고, 화면 안내대로 Enter로 질문을 전송해 결과를 확인했다.
