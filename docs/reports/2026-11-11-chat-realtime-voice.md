# 채팅 Realtime 음성 전환

- 날짜: 2026-11-11
- 기준 HEAD: `2dbc297` (미커밋 작업 트리 변경)
- 상태: 구현·타입 검사·모의 화면 검증 완료. 실제 OpenAI 연결과 사용자 청취 확인 대기.

## 변경

- `POST /api/voice/speak`는 `{ text, sdp }`를 받고, 인증한 사용자의 저장된 OpenAI 키로 `/v1/realtime/calls`에 SDP와 세션 설정을 전송한다. 브라우저에는 `application/sdp`만 반환한다.
- 모델은 공식 문서에 제시된 `gpt-realtime-2.1`, 음성은 `marin`이다. 원문은 기존과 같이 마크다운을 정리해 최대 4,000자까지 읽도록 지시한다. 생성형 모델이므로 원문 그대로의 낭독 충실도는 실제 청취로 확인해야 한다.
- 클라이언트는 수신 전용 WebRTC 트랙을 사용한다. 마이크 권한을 요청하지 않고 `oai-events` 데이터 채널의 `response.create`로 낭독을 시작한다.
- 기존 스피커 버튼과 자동 읽기는 같은 공유 재생기를 사용한다. MP3 생성·전체 버퍼 수신 경로를 제거했다. 음성 입력(녹음 후 전사)은 이번 전환 범위가 아니다.
- `response.done` 뒤에도 출력 버퍼가 비워질 때까지 연결을 유지한다. 중지·다른 답변 선택·화면 이탈·오류·시간 초과 때 요청과 연결을 정리한다.

## 확인

- 관련 Vitest 5개 파일, 27개 테스트 통과. 인증·SDP 검사·키 누락·상위 오류·WebRTC 연결·자동재생 거부·중간 오류·취소·경쟁 조건·화면 이탈을 검증했다. 실제 DB나 유료 API는 호출하지 않았다.
- `npx tsc --noEmit` 통과.
- EGO Lite localhost 채팅에서 실제 스피커 버튼을 누르고 외부 연결 부분만 대체했다. SDP 요청, `response.create`, 수신 전용 연결, 재생 중 표시를 확인했다. 생성 완료 후 재생 표시 유지, 출력 버퍼 종료 후 표시 해제·연결 종료를 확인했다. 대체 코드는 제거하고 새로고침했다.
- 실제 OpenAI 연결·모델 접근 권한·실제 음성의 첫 재생 지연·낭독 충실도·청취는 미확인이다. 테스트에서 유료 API를 호출하지 않는 프로젝트 지침에 따라 사용자의 직접 재생 확인을 남겼다.
- 새 서버 실행, DB 변경, 커밋, 푸시는 하지 않았다. 기존 동시 작업은 보존했다.

## 의심 점검

의심: 실시간 음성이 필요한 출력 경로가 파일 전체 수신에 묶여 있었다.

프로브: `audio/speech`, `speakWithOpenAI`, `response_format.*mp3`, `arrayBuffer`, `.blob`을 음성 출력 경로와 전체 소스에서 대조했다. 기존 호출부·서버 함수·단위 테스트가 원래 경로에 포함됨을 확인했다.

결과: 음성 출력 한 경로의 서버·클라이언트·테스트를 함께 전환했다. 남은 음성 전사 API의 arrayBuffer는 녹음 업로드 처리이며 범위 밖이다.

재발방지: 이전 MP3 헬퍼를 제거해 출력 경로를 하나로 통합했다. SDP 응답 계약, 원격 스트림 재생, 생성 완료와 재생 종료의 차이, 중지 시 취소와 자원 정리를 검사하는 테스트를 추가했다.

## 반복 무음 신고 후 추가 점검

- 사용자 신고: “한번 나왔었는데 지금은 또 안나오네”. 현재 HEAD는 `8278168`이며 관련 파일을 다시 읽었다.
- 기존 EGO 진단 공간 3은 `task space not found: 3`으로 사라졌다. 공간 목록에서 WBS가 열린 사용자 공간 2를 확인했으며 연결 승인을 요청했다. 승인 전에는 해당 공간을 조작하거나 대체 공간을 만들지 않았다.
- 별도 코드 결함 재현: 서버 `output_audio_buffer.started`만 보내도 실제 브라우저 `playing` 없이 재생 표시가 바뀌고 30초 시작 타이머가 해제됐다. 이 조건을 검사하는 테스트가 기존 코드에서 실패하는 것을 확인했다.
- 수정: 서버 전송과 브라우저 `playing`을 모두 확인한 뒤 재생 상태로 바꾼다. 실제 재생 없이 서버 전송이 끝나면 성공 대신 오류를 반환한다. 키·원문·SDP·음성을 저장하지 않는 메모리 진단 기록 `window.__wbsVoiceTrace`를 최대 80건 추가했다.
- 관련 테스트 29개와 `npx tsc --noEmit` 통과. 유료 API는 호출하지 않았다. 실제 사용자 화면·청취·무음의 근본 원인은 연결 승인 대기 중이며 해결됐다고 판정하지 않는다.

의심: 서버 전송 시작을 실제 브라우저 재생으로 간주하면 무음 상태가 성공으로 보이고 시작 제한도 사라진다.

프로브: `onplaying`, `output_audio_buffer.started`, `clearTimeout(startTimer)`를 원래 호출부와 테스트에서 대조했다. 서버 이벤트만 보내는 테스트는 수정 전 실패·수정 후 통과했다.

결과: 동일 모듈 한 곳을 수정했다. 사용자에게 발생한 무음과 같은 원인인지는 아직 미확인이다.

재발방지: 브라우저 재생 없는 서버 전송 시작·종료를 회귀 테스트로 막았다. bugfix 공용 스킬에 진단 프로브를 추가했다.

- 공용 스킬 동기화 실행 결과: Changes 0, Problems 11로 exit 1. paseo 관련 기존 off 설정·잔여 링크 불일치와 Grok ego-browser 잔여 항목이며 이번 음성 코드와 별개다. 해당 설정은 변경하지 않았다.
